# Архитектура переносимого SEO-конвейера

Срез решения: 2026-10-13. Проверенная основа — `seo-article-agents`; технический аудит и публикация на самостоятельный сайт добавляются отдельными ролями.

## Два режима

1. **Отдельный агент.** Получает минимальный явный вход, пишет только свой артефакт и перечисляет `inputs_used`, `missing_inputs`, `status`, `evidence`.
2. **Полный прогон.** Оркестратор читает артефакты, проверяет входные условия и запускает следующий этап. `needs_input` и `failed` не считаются выполнением.

Пользователь может передать готовый текст, план или список запросов. Тогда соответствующий агент нормализует этот вход и отмечает `inputs_used`; генерация текста пропускается, но исследование фактов, SEO-проверка, предпросмотр и публикационные ворота остаются обязательными.

```
site + business goal
  → technical baseline → fix plan → repeat check
  → analytics + demand → intent + page map
  → research dossier + brand brief
  → outline + links → draft + cover + metadata
  → content QA + preview
  → WordPress draft | custom-site draft
  → controlled publication → live checks → monitoring
```

## Артефакты одного запуска

`run.json` содержит `run_id`, `site`, `region`, `business_goal`, версию конвейера, версии источников и ссылки на файлы. Остальные файлы имеют собственные схемы.

| Артефакт | Обязательное доказательство |
|---|---|
| `technical-audit.json` | URL, дата, метод, HTTP/HTML-наблюдение, результат или `not_checked`, причина пропуска |
| `data-snapshot.json` | Поставщик, свойство сайта/счётчик, регион, период, время запроса, квота, статус и сырой файл вне Git |
| `semantic.json` | Запрос, тип частотности и оператор, источник, кластер, гипотеза интента, SERP-проверка |
| `research.json` | Проверяемое утверждение, первичный URL, дата источника, дата проверки, статус цитирования |
| `article-package.json` | Бренд, план, ссылки, тело, обложка, SEO-мета, аудит; неизвестные значения остаются `null` |
| `publication.json` | Адаптер, draft ID/slug, preview URL, решение человека, точный релиз или CMS revision, live URL, проверки, откат |
| `monitoring.json` | Базовый период, будущая дата замера, показатели и фактические данные по мере появления |

Артефакты внутри `runs/` не публикуются в Git без обезличивания. В репозитории допускаются только искусственные примеры.

## Ворота качества

1. **Техника.** Базовый аудит выполнен на целевом сайте. Критичные препятствия публикации и индексации описаны и повторно проверены после исправления.
2. **Спрос и интент.** Есть реальный источник спроса либо честный статус отсутствия доступа. Регион и цель бизнеса известны. Выбранная тема подтверждена SERP и не дублирует существующую страницу.
3. **Редактура.** План покрывает вопросы аудитории. Каждый внешний факт имеет первичный источник. Объём следует полноте ответа; жёсткая длина title, description или статьи не служит доказательством качества.
4. **Предпросмотр.** Автоматический аудит прошёл, изображение и ссылки открываются, человек посмотрел фактическую страницу или черновик. WordPress по умолчанию создаёт только draft.
5. **Продакшен.** Публикация идёт из проверенного состояния. Система записывает точный URL и версию. HTTP, рендер, canonical, robots, sitemap, OG, мобильный вид и откат проверены на живом сайте.

## Адаптеры

- `wordpress`: REST API и application password на сервере; read-back после draft POST; статус `publish` отдельно от создания черновика.
- `custom-site`: реализация зависит от сайта. Адаптер должен предоставить `createDraft`, `readBack`, `publish` и `rollback`; формат хранилища не фиксируется этим репозиторием.
- `static/headless`: будущий адаптер принимает ту же `article-package.json` и обязан вернуть тот же `publication.json`.

## Решения по старому коду

- Переиспользовать 12 skills и WordPress starter с MIT-атрибуцией.
- Перенести методику 14 SEO-чек-листов как знания, а не выдавать её за работающий crawler.
- Взять проверки из `seo_ya` и `seo_leadgen`. Исправить пустые fallback-ответы, неявные зависимости и отсутствие графа ссылок до утверждения полного технического аудита.
- Использовать идеи модульного аудита из `agency-growth-audit-ai` после проверки каждого правила. Клиентские строки и отчёты не копируются.
- Взять из `writer_rerait_moi` идеи свежести, обложек и собственного publisher. Не переносить автоматическое `status=published` как стандарт.
- Не переносить `seo_writer` до удаления раскрытых учётных данных и исправления обработки ошибок.

## Контекст нового запуска

Владелец сайта задаёт регион, бизнес-цель, целевое действие, CMS и точные свойства панелей. Агент не переносит из предыдущего запуска фразы, частотности, счётчики или статус публикации. Каждая роль получает только нужный ей доступ и создаёт новый артефакт с датой проверки.
