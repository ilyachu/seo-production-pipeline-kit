# Адаптер своего сайта

Шаблон публикации для сайта без WordPress. Реализация у каждого сайта своя. Контракт один: на входе проверенный `article-package.json`, на выходе тот же блок `publication`. WordPress REST, application password и `seo-wordpress-publisher` сюда не входят.

Секреты, дампы баз и сырые отчёты в репозиторий и в промпт не кладут. Имена переменных окружения допустимы. Значения — нет.

## Когда вызывать операции

Запись начинается только при `audit.status=pass`. До этого разрешён preflight без изменения данных. Один прогон использует один `publication.adapter`:

| Адаптер | Skill | Первая запись |
|---|---|---|
| `wordpress` | `seo-wordpress-publisher` | CMS draft |
| `custom-site` | `seo-custom-site-publisher` | `createDraft` этой реализации |

`publication.implementation` называет конкретный импортёр. Это не второй универсальный API.

## Операции

Реализация предоставляет четыре операции. Имена можно сопоставить со своими функциями, но смысл и порядок сохраняются.

### createDraft

Идемпотентно создаёт или обновляет одну запись со статусом draft.

Вход:

- пакет статьи: тело, мета, slug, канонический URL, обложка, ссылки;
- `implementation`;
- стабильный ключ импорта, который повторяется при повторе той же статьи;
- путь к копии данных для первого прогона и отдельно к рабочим данным для второй, уже подтверждённой вставки;
- ожидаемый URL черновика или предпросмотра.

Порядок:

1. Dry-run: проверить схему payload, уникальность slug и что ключ не указывает на чужую запись. Данные не менять.
2. Реальная вставка только в draft. Не выставлять публичный статус.
3. Вернуть `draft_id`, ключ импорта, `preview_url` и ревизию данных.

Повтор с тем же ключом обновляет ту же запись, а не создаёт вторую.

### readBack

Читает запись тем же путём, которым её увидит предпросмотр, и сравнивает с отправленным payload.

Обязательные поля сверки: статус draft, slug, заголовок, канонический путь, хеш тела. Расхождение возвращает `failed` и список полей. HTTP-код вставки без чтения не считается успехом.

Предпросмотр после успешного read-back: открыть страницу черновика на desktop и mobile, проверить обложку и ссылки. Это ещё не live URL.

### publish

Отдельное действие после явного подтверждения человека для конкретного `draft_id`.

1. Ещё раз прочитать запись и убедиться, что ключ, slug и хеш те же.
2. Перевести в публичный статус только эту запись.
3. Вернуть точный `live_url`, ревизию кода или данных и время.

Пока человек не назвал этот `draft_id`, операция не вызывается.

### rollback

План пишется до `publish`. Откат удаляет или возвращает в draft только запись с этим ключом. Остальные записи не восстанавливаются из старого полного дампа. Откат кода — отдельный шаг и только если сломался сам релиз, к ранее записанной ревизии.

После отката повторить чтение записи и публичный список материалов.

## Результат в пакете

```json
{
  "status": "needs_input",
  "adapter": "custom-site",
  "implementation": "<site-importer-id>",
  "mode": "draft",
  "draft_id": null,
  "preview_url": null,
  "read_back": {
    "status": "not_checked",
    "compared_fields": ["status", "slug", "title", "canonical", "body_sha256"],
    "reason": "createDraft ещё не вызывался"
  },
  "human_decision": null,
  "release_sha": null,
  "live_url": null,
  "live_checks": {
    "http": {"status": "not_checked", "reason": "publish ещё не выполнен"},
    "render_desktop": {"status": "not_checked", "reason": "нет живого URL"},
    "render_mobile": {"status": "not_checked", "reason": "нет живого URL"},
    "canonical": {"status": "not_checked", "reason": "нет живого URL"},
    "robots": {"status": "not_checked", "reason": "нет живого URL"},
    "sitemap": {"status": "not_checked", "reason": "нет живого URL"},
    "og": {"status": "not_checked", "reason": "нет живого URL"}
  },
  "rollback": {
    "status": "ready",
    "plan": "Вернуть в draft или удалить только запись с этим ключом импорта."
  }
}
```

`publication.status=ready` допустим, когда `live_url` открыт и каждый пункт `live_checks` имеет `pass`. `not_checked` обязан содержать `reason` и оставляет публикацию незавершённой.

Минимальная сигнатура, которую копируют в репозиторий сайта, без привязки к фреймворку:

```text
createDraft(payload, target) -> { draft_id, import_key, preview_url, data_revision }
readBack(draft_id) -> { status, slug, title, canonical, body_sha256 }
publish(draft_id, confirmation) -> { live_url, release }
rollback(draft_id) -> { resulting_status }
```

`target` указывает копию или рабочие данные. Код адаптера живёт в репозитории сайта. Здесь только контракт.

## Что реализовать в репозитории сайта

Адаптер может писать в SQLite, другую БД или CMS API. Он должен иметь свой идентификатор `implementation`, стабильный ключ статьи, проверку уникальности slug и четыре операции выше. Черновик проверяется тем же рендером, который увидит читатель. Перед release укажите хранилище, права, backup, точный SHA и порядок отката в runbook сайта.

Исходный код, учётные данные и рабочую базу конкретного сайта в этот универсальный пакет не копируют. Живой URL после publish проверяют отдельно: HTTP, desktop/mobile, canonical, robots, sitemap, OG и медиа. Индексация в этот момент не обещается.
